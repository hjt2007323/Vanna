## 一页版：问题 → 上游行为 → 我的改动 → 为什么 → 实际结果 → 边界

**问题（一句话）**
Vanna 2.0.2 的 SQLite Runner 用“SQL 第一个词是不是 SELECT”来判断语句类型，导致带前导注释的 SELECT、`WITH … SELECT`、`VALUES`、`INSERT … RETURNING` 被当成写语句；空结果则丢掉列定义。

**上游行为（实测，不是转述）**

- `-- 注释\nSELECT …` → 返回 `rows_affected=-1`，真正的行被丢掉；
- `WITH … SELECT`、`VALUES` → 同样 `rows_affected=-1`；
- `INSERT … RETURNING` → `OperationalError: cannot commit transaction - SQL statements in progress`（结果集没取完就 commit）；
- `SELECT … WHERE 0` → 返回 `(0,0)` 的空 DataFrame，列名丢失；
- 空 SQL → `IndexError`；
- 重复列名（`id AS k, name AS k`）→ 只剩一列。

**我的改动（最小面）**

1. 用 `cursor.description` 判断“这条语句有没有结果集”，不再解析首词；
2. 空结果按 `description` 的列名建 `(0,n)` DataFrame，保留列序；
3. `RETURNING` 先 `fetchall()` 再按 `conn.in_transaction` 提交，保证“返回行 + 真落库”；
4. DataFrame 改为按位置构造，重复列名不再合并；
5. 新增可选 `read_only=False`：`mode=ro` URI（`Path.as_uri()` 编码路径）+ `PRAGMA query_only` + SQLite authorizer（拒写、拒 ATTACH/DETACH/DDL、拒可写 PRAGMA），缺库不创建；
6. 空 SQL 给明确 `ValueError`。

**为什么这样做**

- `description` 是数据库自己对结果集的描述，天然覆盖注释/CTE/VALUES/RETURNING/行返回 PRAGMA，也不像正则那样能被 `WITH … DELETE` 绕过；
- 提交时机属于事务语义：必须在结果集消费完之后提交，否则 SQLite 会拒绝，而关闭连接会回滚；
- 只读必须是**数据库机制**而不是关键词检查：文件级 `mode=ro` + 连接级 `query_only` + 语句级 authorizer 三层叠加，才算“拒写”而不是“看起来拒写”。

**实际结果（同一批 29 条输入、同一环境）**

- 冻结上游基线 7/29 符合预期 → 修后 29/29；
- 44 条新增回归测试 + 7 条上游受影响测试全部通过；
- 只读模式下 INSERT/UPDATE/DELETE/CTE 写/DDL/ATTACH/`VACUUM INTO`/写 PRAGMA/`load_extension` 全部被拒，数据库文件 SHA256 不变；
- 默认 INSERT/UPDATE/DELETE 仍提交，重连可见；异常后连接释放、文件可删。

**边界（敢说“不”）**

- 只改 SQLite Runner；其他数据库 Runner 未动也未回归；
- 只在 Python 3.14.6 / SQLite 3.53.2 实测；Python <3.11 的 authorizer 降级路径未实测；
- 只读只支持已存在的文件路径，不支持 `:memory:`/`file:` URI；
- 未向上游提 PR（仓库已 archived），不声称被接收；
- 未做并发/大库性能测试，没有任何性能数字。

## 常见追问与答法（只答事实）

| 追问 | 回答要点 |
|---|---|
| 为什么不用正则/SQL 解析？ | 数据库已经给出 `description`；正则既容易漏（注释/CTE/RETURNING），又容易被 `WITH … DELETE` 绕过。 |
| 为什么 `RETURNING` 要单独处理？ | 它既有结果集又有写事务；上游在结果集未取完时 commit，SQLite 会拒绝。先取完再提交，两者都满足。 |
| 只读为什么用三层？ | 文件级 `mode=ro` 防写文件，连接级 `query_only` 防写事务（含 CTE/触发器），authorizer 防 `ATTACH`、DDL、写 PRAGMA 这类“不写主库但有副作用”的路径。 |
| 改动会不会破坏默认写？ | 不会：非结果集语句仍是 `commit()` + `rows_affected`；V5/V5b/V11 回归项在 before/after 两侧都通过。 |
| 最大的风险是什么？ | 行为变化点：默认模式下 `PRAGMA table_info` 等行返回语句现在返回行而不是 `rows_affected`。这是 `description` 判定的必然结果，已在交付文档里写明，并提供 before/after 对照。 |
| 你个人做了什么？ | 复现、修复、只读设计、测试、复跑脚本与演示、证据与文档；上游代码只有这一个文件被改。 |
