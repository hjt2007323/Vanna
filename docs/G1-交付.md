## 3. 上游实际行为：先复现，再改

测试输入先各自在独立 SQLite 里确认语法有效（`V7c` 就因此被我们自己抓出过一次：`AS escape` 里的 `escape` 是关键字，语句本身语法错误，已改成 `AS side_db` 后重测——不用“写错的 SQL”证明“库有 bug”）。

冻结基线（`baseline/upstream_sql_runner.py`）真实运行结果，节选：

| 输入 | 上游实际返回 |
|---|---|
| `-- 注释\nSELECT id, name FROM products` | `rows_affected = -1`（行被当写语句丢掉） |
| `WITH cheap AS (…) SELECT …` | `rows_affected = -1` |
| `VALUES (1,'alpha'),(2,'beta')` | `rows_affected = -1` |
| `SELECT id, name … WHERE id < 0` | `pd.DataFrame()`，shape `(0,0)`，列全丢 |
| `INSERT … RETURNING id, name` | **`OperationalError: cannot commit transaction - SQL statements in progress`** |
| `UPDATE … WHERE id=-999 RETURNING id` | `rows_affected = 0`（RETURNING 结果被丢） |
| `SELECT id AS k, name AS k …` | 只剩 1 列 `['k']` |
| `PRAGMA table_info(products)`（默认模式） | `rows_affected = -1` |
| `""`（空 SQL） | `IndexError: list index out of range` |
| `INSERT/UPDATE/DELETE`（普通） | `rows_affected = n`，且重连可见（正常） |

两个在任务卡里没写细、但复现出来的事实：

1. `RETURNING` 不是“悄悄丢行”，而是**直接抛异常**——上游在还有未取完的结果集时就 `commit()`，SQLite 拒绝。这是真实可复现的崩溃，不是理论风险。
2. 空 SQL 的 `IndexError` 确实可达（`cursor.execute("")` 不报错，是后面的 `split()[0]` 崩）。

基线整体计数（`docs/evidence/baseline/`）：**29 条输入里 7 条符合预期，13 条返回行，4 条报错，12 条不支持**（12 条即 `read_only` 相关；上游没有这个参数，构造时就 `TypeError`，不是它的 bug）。

核心源码改动（`git show 95dd9e2 -- src/…/sql_runner.py` 的关键 hunk）：

```diff
-            # Determine if this is a SELECT query or modification query
-            query_type = args.sql.strip().upper().split()[0]
-
-            if query_type == "SELECT":
-                rows = cursor.fetchall()
-                if not rows:
-                    return pd.DataFrame()
-                results_data = [dict(row) for row in rows]
-                return pd.DataFrame(results_data)
-            else:
-                conn.commit()
-                rows_affected = cursor.rowcount
-                return pd.DataFrame({"rows_affected": [rows_affected]})
+            if cursor.description is not None:
+                columns = [column[0] for column in cursor.description]
+                rows = cursor.fetchall()
+                if conn.in_transaction:
+                    conn.commit()
+                if not rows:
+                    return pd.DataFrame([], columns=columns)
+                return pd.DataFrame([tuple(row) for row in rows], columns=columns)
+
+            conn.commit()
+            return pd.DataFrame({"rows_affected": [cursor.rowcount]})
```

### 4.2 三个修复点为什么这样做

1. **用 `cursor.description` 判结果集**，不解析 SQL 文本。`description` 是 SQLite 自己给出的“这条语句有没有结果集”，`SELECT`/`COMMENT+SELECT`/`WITH…SELECT`/`VALUES`/`RETURNING`/行返回 `PRAGMA` 都自然覆盖；不用拼正则可绕过的首词分类。
2. **空结果用 `description` 里的列名建 DataFrame**，`(0,n)` 且列序保留；不是“返回空表就当没有列”。
3. **RETURNING 先 `fetchall()` 再 `commit()`**：写事务是否要提交用 `conn.in_transaction` 判断（普通 `SELECT` 不开事务，不会误提交），显式 commit 后关闭连接也不会回滚；`INSERT … RETURNING` 因此既返回行也真正落库。非结果集语句仍走原来的 `commit()` + `rows_affected`，不破坏默认写语义。
4. DataFrame 改为**按位置**从游标列构造（原来是 `dict(row)`），顺带修掉重复列名被合并丢列的问题；正常单名列的输出与上游一致。

### 4.3 只读模式（`read_only=True`，默认 `False`）

四层防护，不依赖 SQL 关键字：

```python
# 1) 缺库直接拒绝，不创建
if not path.exists():
    raise FileNotFoundError(... "(read_only=True never creates a database)")
# 2) 路径经 Path.as_uri() 百分号编码（空格/#/中文/% 都不会截断 URI），再加 mode=ro
uri = f"{path.resolve().as_uri()}?mode=ro"
conn = sqlite3.connect(uri, uri=True)
# 3) 连接级：引擎拒绝写，包括藏在 CTE/触发器里的写
conn.execute("PRAGMA query_only = ON")
# 4) 语句级：authorizer 拒绝写动作、ATTACH/DETACH、DDL、以及可写型 PRAGMA
conn.set_authorizer(self._authorize)   # Python 3.11+；低版本自动降级为 2+3 层
```

- **PRAGMA 策略（本项目明确记录）**：只允许元数据只读白名单（`table_info`、`table_xinfo`、`table_list`、`index_info`、`index_list`、`index_xinfo`、`foreign_key_list`、`foreign_key_check`、`integrity_check`、`quick_check`、`database_list`、`collation_list`、`compile_options`、`freelist_count`、`page_count`、`page_size`、`schema_version`），其余一律拒绝——包括 `user_version=`、`journal_mode=`、`writable_schema`、`optimize`。不做“所有 PRAGMA 一刀切”，也不是“全部放开”。
- **扩展加载**：Python `sqlite3` 默认不启用扩展加载，实测 `SELECT load_extension(...)` 返回 `OperationalError: not authorized`；只读连接上不调用 `enable_load_extension`。
- `:memory:` 与 URI 形式的 `database_path` 不支持只读，直接给明确错误，不静默降级。

## 9. 兼容性与行为变化（明确声明）

**保持不变**：`SqliteRunner(database_path)` 位置参数与默认行为；`run_sql(args, context)` 的 async 签名与 `pd.DataFrame` 返回类型；非结果集语句的 `commit()` 与 `{"rows_affected":[…]}` 契约；每次调用新建/关闭连接；`row_factory` 仍为 `sqlite3.Row`；其他数据库 Runner 未动。

**有意变化（会写进提交说明，不静默）**：

1. 任何**有结果集**的语句都按结果集返回，因此默认模式下 `PRAGMA table_info(...)`、`EXPLAIN …` 也从 `rows_affected=-1` 变成返回行——这是 `description` 判定的直接结果，且比丢结果更正确。
2. `INSERT/UPDATE/DELETE … RETURNING` 从“抛异常/丢结果”变成“返回行 + 真正提交”。
3. 重复列名不再被合并（`SELECT id AS k, name AS k` 返回两列）。
4. 空 SQL 从 `IndexError` 变为明确的 `ValueError`。
5. 新增可选参数 `read_only=False`；默认不启用，不影响既有调用。

## 12. 学习点（3–5 条，均为本次实际踩到）

1. **“按首词判语句类型”在数据库里必错**。`SELECT` 只是 SQL 的一种；注释、CTE、`VALUES`、`RETURNING` 都能返回行。数据库已经给了 `cursor.description`，用它比用字符串规则稳，也不容易被 `WITH … DELETE` 绕过。
2. **提交时机是事务语义，不是收尾动作**。上游 `RETURNING` 崩溃不是“少个 commit”，而是“结果集没消费完就 commit”。先 `fetchall()` 再按 `in_transaction` 提交，才同时满足“返回行”和“真落库”。
3. **只读不能靠 SQL 关键词**。真正管用的是数据库机制：`mode=ro`（文件级）、`PRAGMA query_only`（连接级）、authorizer（语句级）叠加；`ATTACH`、`VACUUM INTO`、写 PRAGMA 这类“不是 INSERT 也能写”的路径要单独验证。
4. **URI 编码是路径问题的高发点**。`#` 在 URI 里是 fragment，空格要转义；`Path.as_uri()` 一次解决空格/`#`/中文/`%`，比手拼 `file:` 字符串可靠。
5. **证据要能证伪**。这次自己的探针先写出了 `AS escape` 的语法错误用例——如果没先确认 SQL 本身有效，就会把“我的 SQL 写错了”当成“库有 bug”。基线哈希校验、独立临时库、每次重新建库，都是为了让 before/after 站得住。
